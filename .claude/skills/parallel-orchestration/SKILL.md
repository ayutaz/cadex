# 担当への分け方と待ち方（cadex / robot-project）

## 原則

並列の原則は、ルール `parallel-by-default.md` にある。このスキルは、その原則をこのリポジトリの場面で
**どう分けるか**の手順と型を示す。分け方は「誰が何の結果を待つか」だけで決める。
待たないものは、**最初の応答で全部**起動する。

## 1. 待ちの表を書いてから起動する

手を動かす前に、塊ごとに次の表を書く（頭の中でなく、応答に書く）。

| 塊 | 待つ結果 | 触るファイル | 担当 |
|---|---|---|---|

- 「待つ結果」が空の塊は、**全部を最初の応答で同時に起動する**。1つずつ起動しない。
- 「待つ結果」は、**その塊が本当に使う結果**だけを書く。「学習が終わってから動画」ではなく、
  動画のうち学習の結果を使うのはトレースだけ。カメラ・文字・カードの準備は待たない。
- 1つの塊が「借りる・回す・回収・評価・比較・破棄」のように並んでいたら、それぞれの行に分けて
  待つ結果を書き直す。GPU が要らない行（計算・確認・枠づくり）は、たいてい何も待たない。
- 「触るファイル」が重なる2つの塊は、1人にまとめる（3. を参照）。
- Skill を読むのは、起動と同じ応答でよい。担当には、読むべき Skill の名前を指示に書いて渡す。

## 2. このリポジトリでよく出る分け方

段の名前は q8-* スキルに合わせる。左の列は最初の応答で同時に起動し、右の列は待つ結果が届いてから起動する。

| 場面 | 最初の応答で同時に | 届いてから |
|---|---|---|
| 新しい機体（`q8-body-variants`） | 機体の作成と実ビルドの判定（手順3〜4） / 学習設定 `configs/train_full_<機体>.json` とテスト `tests/test_vastai_config.py` / 歩けるかと報酬の抜け道の確認（手順5〜6、紙と `fewest_support`） / 動画の素材の準備（カメラ・文字・カード。`q8-sim-video`） / 文書の枠（`docs/experiment-results.md` の節の見出しと表の空欄） | バンドル（機体のカットモデル）→ GPU 学習 → 評価・比較 → 動画の仕上げ・文書の数値 |
| GPU で新しい報酬を試す（`q8-vastai-gpu-training`） | 報酬の抜け道の計算（GPU 不要。「歩かずにこの項を最大にする動き」で点が入らないか） / 借りる前の確認（イメージのタグ、バンドルの時刻）と借りて回す / 比較の枠（`compare_seeds.py` の引数と、比べる相手の結果） | 評価は**届いた回から**並行して回す（全部の回を待たない） / 破棄の確認は全部の回収のあと |
| 評価・動画・文書 | 評価 / 動画の素材 / 文書の枠 | 動画の仕上げ・文書の数値（評価の結果を待つ） |
| レビュー | 終わった範囲から、範囲ごとに1人 | 残りの範囲は、終わりしだい |
| レビューの指摘の修正 | **ファイルごと**に1人 | 依存する指摘（I2 が I1 の直し方に左右される）は、同じ担当にまとめる |

担当が GPU の待ちを抱えるときも、評価・比較・破棄の確認を同じ担当に順番に抱えさせない。
評価は別の担当にし、回収された回のフォルダ（`artifacts/runs/vastai/<run>/`）を見て始めさせる。

## 3. 同じファイルの衝突を避ける

- **ファイルごとに持ち主を1人決め**、起動の指示に「触ってよいファイル」と「触らないファイル」を書く。
  `docs/experiment-results.md` や `tests/test_vastai_config.py` のような共有のファイルは、特に1人に絞る。
- 2つの作業が同じファイルを書き換えるなら、その2つは1人にまとめる。分けたまま順番を約束しない。
- コミットは**パスを指定**して `git add <パス>` する。`git add -A`、`git add .`、`git commit -a` は使わない。
  ほかの担当の書きかけが入る。
- ほかの担当が並行して編集しているフォルダ（例: `robot-project/`）は、指示に「触らない」と書く。

## 4. 起動の指示に必ず入れるもの

担当に渡す指示は、次の項目をこの順で持つ。

1. **目的**と、終わりの状態（何ができたら終わりか）。
2. **読む Skill**（例: `q8-body-variants`、`q8-vastai-gpu-training`）。
3. **触ってよいファイル**と、**触らないファイル・フォルダ**。
4. **使ってよいもの**（GPU の台数と予算、承認が要る操作）。
5. **禁止**: ディスク全体の検索（`find /`、`find ~`、`grep -r ~`）をしない。探す範囲はフォルダで指定する。
6. **時間のかかるコマンド**には `timeout` を付けるか、ログをファイルに出して裏で走らせる。
7. **進捗の報告**: 区切り（ビルド・判定・学習の開始・回収・評価）ごとに SendMessage で1行送る。
8. **自分で確かめる**: 知らせを待たず、ログの末尾・成果物の更新時刻を自分で見に行く。

## 5. 待つときの決まり

- 終わりの知らせだけに頼らない。知らせは届かないことがある（2026-11-18 に2回、35〜45 分止まった）。
- **担当を起動した同じ応答で、CronCreate の15分ごとの見張りを置く。** CronCreate は遅延読み込みのツールなので、
  定義がまだ無ければ、**最初の応答で `ToolSearch`（`select:CronCreate,CronDelete,TaskStop`）を担当の起動と並べて**呼び、
  次の応答の最初で CronCreate を呼ぶ。読み込みのために担当の起動を後回しにしない。見張りは、各担当の最後の報告・
  ログの末尾・成果物の更新時刻を見る。終わっているのに動いていない担当がいれば、知らせを待たずに次の段を
  起動する（次の段は新しい担当にする。6. を参照）。全部終わったら CronDelete で消す。
- 担当にも、自分の待ち（sweep など）に15分ごとに起きる仕掛け（Monitor か `sleep 900`）を置かせる
  （`q8-vastai-gpu-training` の「終わりを待つ」）。
- 待つあいだ、自分は次の段の準備（差分のまとめ、要件の切り出し）を進める。

## 6. 分担は起動のときに決め、後から変えない

**動いている担当にも、終わった担当にも、分担の変更や新しい作業を SendMessage で送らない。**
届くのが遅れた指示に従い、担当が文書を存在しない動画の名前に書き換えて、コミットまでした例がある。

新しい作業や分担の変更が要るときは、次のとおりにする。

1. 動いている担当がその作業と同じファイルを触るなら、その担当は TaskStop で止める。
2. **新しい担当を起動**し、4. の指示に、ここまでの分（何ができていて、何が残っているか、
   実在するファイルの名前）と、触ってよいファイルを書いて渡す。
3. 終わった担当には何も送らない。

SendMessage で担当に送ってよいのは、**今の分担のまま**の再開（「sweep は終わっている。評価に進んで」）と、
質問への答えだけ。

| 言い訳 | 現実 |
|---|---|
| 「終わった担当は文脈を持っているので、続きを頼むほうが早い」 | 古い文脈で動き、すれ違う。ここまでの分を指示に書けば、新しい担当で足りる |
| 「小さな変更なので、一言送れば済む」 | 届く順番と時刻は保証されない。小さな変更でも新しい担当にする |
| 「動いている担当に、ついでに頼む」 | 分担が変わると、触ってよいファイルの約束が壊れる |

## 7. 担当が止まったとき

- **見分け方**: 動作中のはずなのに、担当の触るファイルもログも30分以上動かない。
  1. `ps -eo pid,etime,command | grep -E 'find|grep|rsync|python' | grep -v grep` で、長く走るコマンドを探す
     （例: ディスク全体の `find`）。見つけたら、そのプロセスだけを止める。
  2. Mac のスリープで止まることもある。`pmset -g log | grep -E 'Sleep|Wake' | tail -n 5` で、
     止まった時刻にスリープが無いかを見る。
- **立て直し方**: 止まった担当は TaskStop で止め、**ここまでの分を書いた新しい担当**で引き継ぐ
  （何ができていて、何が残っているか。フォルダの中身を `ls -lt` で見て書く）。止まった担当を再開させない。

## よくある間違い

| 間違い | 正しくは |
|---|---|
| 最初の応答でビルドの担当だけを起動し、学習・動画・文書を後から順に起動する | 待ちの表を書き、待たない塊（設定・テスト・抜け道の確認・動画の素材・文書の枠）を同時に起動する |
| 学習の担当1人に、借りる・回す・回収・評価・比較・破棄を全部抱えさせる | 抜け道の計算と比較の枠は最初に別の担当。評価は届いた回から別の担当 |
| 動画と文書を、学習が終わってから始める | 素材と枠は先に作る。学習の結果を使う仕上げだけを待つ |
| 同じファイルを触る指摘を、別の担当に分ける | ファイルの持ち主を1人にし、その2つをまとめる |
| 「終わりの知らせを待てば足りる」 | 起動と同じ応答で、CronCreate の15分ごとの見張りを置く |
| 終わった担当に SendMessage で新しい依頼を送る | 新しい担当に、ここまでの分と触ってよいファイルを書いて渡す |
| `git add -A` でまとめてコミットする | パスを指定して `git add` する |
| 担当が止まっても、知らせを待ち続ける | 30分動かなければ、`ps` とスリープを見て、新しい担当で引き継ぐ |
