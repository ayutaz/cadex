# 形の派生を足して、作って、学習するまで（robot-project）

## 原則

形の派生は、**既定値の機体を1バイトも変えず**に足す。偽の API のテストが通っても、形と学習はまだ
何も保証されていない。実ビルドの判定と、物理的に歩けるかと、報酬のずるい取り方を、GPU に載せる前に
確かめる。学習は**少ない回数で先に**確かめる。

## 手順（この順で。飛ばさない）

1. **基準ログを先に取る（変える前のコミットで）。**
   - 変える前のコミットの `quadruped8.py` で、偽の API（`tests/test_design_battery.py` の `run_design`）の
     宣言の列を `tests/data/design_log_<名前>.json` に保存する。前例は `tests/test_design_tail.py`、
     `tests/test_design_tripod.py`（既定値と `mini-r2-p7-eff` の2つ）。
   - 新しい params の既定値で、その基準と一致することをテストで固定する（TDD: 先に書く）。
2. **脚・関節・足の数を決め打ちしない。**
   - `q8.robot` の `model_legs`・`model_joints`・`model_feet` で、モデルから読む。
   - physics の判定は `q8.physics.fewest_support`。
   - 評価の足は `success.feet`、無ければ `model_feet`。
   - 脚の名前は四足が `lf, rf, lh, rh`、3本足が `lf, rf, hc`（`q8/robot.py` の `LEGS` は四足の4本だけ。3本足はモデルの `hip_<脚>` から `model_legs` で読む）。
     `["lf","rf","lh","rh"]` や `8` を書いたら、そこが3本足・6本足で `KeyError` になるか、黙って誤る。
3. **既定値の実ビルドで1バイト比べる。**
   - 既存の機体（例: `mini-r2-p7-eff`）を、同じ params のまま別名（例: `mini-r2-p7-eff-chk`）で作り直す。
   - `robot/mjcf/<機体>/` の `model-model.xml`・`walk-task.json`・`cut/*` を `cmp` で比べる。
   - `visual.xml` はメッシュのパスに機体名が入るので、差が出てよい。それ以外の差は不具合。
   - 確かめたら、別名の出力（`artifacts/`、`robot/meshes/`、`robot/mjcf/` の別名）と
     `~/cadex-projects/quadruped8-<別名>` を消す。
4. **派生の機体を実ビルドし、判定を全部見る。** 偽の API では次が見えなかった。
   - 台が胴体の上下の分割からはみ出す。
   - サーボどうしが重なる。
   - リード線の通り道が無い。
   - 判定が脚の数の違いで `KeyError` になる。
   - 中実の部分で質量が 24 g 増える。
   - 衝突形状の無い部品が床にめり込む。

   見るものは次の4つ。どれか1つでも欠けたら、形を直してから先へ進む。

   | 見るもの | 場所 | 合格 |
   |---|---|---|
   | 設計の判定 | `artifacts/<機体>/design_report.json` の `verdict` | 全部 `true` |
   | 組立の判定 | `uv run python scripts/assembly_guide.py --variant <機体>` → `artifacts/<機体>/assembly/print_plan.json` の `assembly_verdict` | 全部 `true` |
   | 質量 | `design_report.json` の `physics` | 元の機体と比べて増えた分を説明できる |
   | 衝突形状 | `model-model.xml` | 足した部品（台・ハウジング・しっぽ）すべてに衝突の geom がある |
5. **物理的に歩けるかを、学習の前に確かめる。** 歩き方で1本を上げたとき、残りの足で静的に
   立てるか（重心が残りの足の支持多角形に入るか）を、紙の上か `fewest_support` で見る。
   3本足は1本を上げると静的に立てない。立てないなら、動的な歩き方が要る前提で報酬を設計する。
   立てない前提のまま学習を回しても、合格率は 0 になりうる（tri-r2 は 0 だった）。
6. **報酬のずるい取り方を、学習の前に見直す。** 下の表の各行を、新しい報酬と新しい形に当てはめる。
7. **形を直したら、それを元にした機体を全部作り直す。**
   - カットモデル（`robot/mjcf/<機体>/cut/`）は `build_robot.py` で作り直す。学習用バンドルも
     `q8/dr_bundle.py` で作り直す。`--source` と `--out` は機体名ではなく**フォルダのパス**（cwd は `robot-project`）。
     ```bash
     uv run python scripts/make_dr_bundle.py --source robot/mjcf/<機体>/cut --out artifacts/<機体>-dr/cut
     ```
   - 古い形のものを使っていないか、ビルドの時刻と、形を直したコミットの時刻を比べる。
     ```bash
     git log -1 --format=%ci -- robot-project/robot/design/quadruped8.py
     stat -f '%Sm %N' robot-project/robot/mjcf/<機体>/cut/* robot-project/artifacts/<機体>-dr/cut/*
     ```
     バンドルが古ければ作り直す。「昨日作ったバンドルがある」は、使ってよい理由にならない。
8. **少ない回数で先に学習する。** シード3回で合格率と歩き方を見て、良ければ回数を増やす。
   本番の回数（5シード以上）を最初から回さない。形の派生は、学習でうまくいくとは限らない。
9. **印刷に向けて要対応の点を残す。** シミュレーションだけの範囲でも、実機で詰まる点
   （例: しっぽのサーボが差し込めない）を、レポートやコミットのメッセージに書いて残す。

機体の作り方・学習設定・残し方・コミットは `q8-artifacts-and-publishing`、GPU は `q8-vastai-gpu-training` に従う。

## 報酬のずるい取り方（見つかったもの）

| ずるい取り方 | 起きる理由 | 直し方 |
|---|---|---|
| 3本を同時に浮かせて跳ねる | 足上げの報酬を全部の脚に払うと、何本も上げるほど得になる | ほかの脚が接地しているときだけ払う |
| 立っているだけで点が入る | 位相の報酬が、動かなくても正の値になる | 平均を引いて、立っているだけなら 0 にする |
| 胴体を前後に揺すって速度を稼ぐ | どの機体でも `c_chassis` の xbody 原点は床の高さ（重心の約 65 mm 下）にあり、`vel` はその点の速度（v_com + ω × r）なので、胴体のピッチの揺れで `vel_x` が水増しされる。3本足のように歩けない形で効く | 体全体の重心の速度（`centre_of_mass_velocity`）か、一定時間の重心の変位で読む。揺すって点が入らないことを確かめる |

四足（しっぽ付きを含む）にも同じ抜け道はあるが、揺れが小さく（原点の速度の標準偏差 17 mm/s）、合格は別の指標（`speed_ratio`・`steps_min`）で測るので、既存の合格率は水増しされていない。観測を替えると既定値の `walk-task.json` が変わるので、直すのは別の計画（既定を守る切り替えの params と四足の A/B）にする。

新しい報酬項を足したら、「歩かずにこの項を最大にする動き」を1つ考え、それで点が入らないことを確かめる。

## 基準ログの扱い

- 基準ログとの比較が落ちたら、**既定値の出力が変わった**ということ。差が 0.5 mm でも直すのはコード。
- **基準を今のコードで作り直さない。** 作り直すと、比べる相手が無くなり、テストが意味を失う。
- 既定値の出力を変えることが本当に意図なら、それは形の変更。依頼者の了承を取り、
  既存の機体と、それを元にしたバンドルを全部作り直す（手順7）。基準も、変えた理由と
  変える前のコミットを書いて更新する。

## zsh の `--set`

`build_robot.py` の `--set` は、1つずつ書き下す。zsh では `$args` が単語に分かれないので、ループで
組み立てた文字列が1つの引数で渡り、名前に空白の入った機体のフォルダができた。できたら消して作り直す。

```bash
uv run python scripts/build_robot.py --variant mini-r2-tail1 --set body_length=96 --set tail_dof=1 ...
```

## よくある間違い

| 間違い | 正しくは |
|---|---|
| 偽の API のテストが通ったので、実ビルドせずに学習へ進む | 実ビルドして、`verdict`・`assembly_verdict`・質量・衝突形状を見る |
| 基準ログを今のコードで作り直してテストを通す | コードを直して、既定値の出力を元に戻す |
| 既定値の確認を偽の API だけで済ませる | 既存の機体を別名で作り直し、`cmp` で1バイト比べる |
| 形を直したあと、前に作ったバンドルで学習する | バンドルを作り直し、時刻をコミットと比べる |
| 脚名のリストや関節の数を書く | `model_legs`・`model_joints`・`model_feet` で読む |
| 足上げを全部の脚に払う | ほかの脚が接地しているときだけ払う |
| 新しい形を、いきなり本番の5シードで回す | シード3回で先に確かめる |
| 歩けるかを学習の結果で初めて知る | 1本を上げたときに静的に立てるかを、学習の前に見る |
| シミュレーションだけだからと、実機の不具合を書かない | 印刷に向けて要対応の点を残す |
| 「急いでいる」ので手順4〜6を飛ばす | 飛ばすと、外れた学習で GPU の時間を失う。急ぐときこそ回数を減らす（手順8） |
