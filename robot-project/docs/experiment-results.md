# 実験結果

最終確認日: 2026-11-19

すべてシミュレーション（MuJoCo 3.10）の結果で、実機では確かめていない。
評価は Cadex の `cadex evaluate` で行った。エンジンのモデル（カットではない方）で、成功条件の10シード（2101〜2110）を使う。
固定歩容も、Cadexと同じ指標計算（`CadexEvaluation`）で評価した（`q8/evaluation.py`）。

## 1. 成功条件（タスクに書いたもの）

| id | 指標 | 条件 |
|---|---|---|
| completes | 最後まで転倒・沈み込みなし | = 1 |
| upright | 最大傾斜 | ≤ 25° |
| walks | 最少の脚の歩数（滞空0.1秒以上、腰高の0.15倍以上離れて着地） | ≥ 4 |
| speed | 速度比（実速度 / 指令） | 0.5〜1.5 |
| rated | 最も重い関節の RMS トルク / 推定連続定格（失速の40%） | ≤ 1.0 |

指令速度は 40〜160 mm/s から4秒ごとに引き直す。エピソードは8秒、制御は50 Hz。

## 2. 学習の経過（基準機体、CPU、学習用カットモデル、512環境）

|---|---|---|---|---|---|---|

| v2（`cpu-cut-v2`） | v1＋定格比の4乗・傾きの罰 | 1000 | 10.2 M | 18.5 分 | 5/10（最終） | 5/10 |

（v1とv2は同時に走らせたので、それぞれの時間は単独で走らせた場合より長い。）

チェックポイントごとの値は `artifacts/training/<run>/checkpoints.csv` にある。主な傾向は次のとおり。

- **v1**: 100反復目で目標速度に追従し（速度比1.04）、各脚が約15歩を踏んだ。
  - 1000反復まで、最も重い関節（左前脚の股）の RMS トルクが推定連続定格の **1.4倍** から下がらなかった。
  - 傾きも約15°と大きかった。
  - 歩き方が左右非対称で、負荷が片側の前脚に集中していた。
- **v2**: 負荷と傾きは下がった（定格比0.60、傾き5°）。
  - 代わりに足を上げない「すり足」に寄り、歩数の条件で落ちるシードが増えた。
- **v3**: 足上げの重みを上げると、100反復目で6/10に達した。
  - その後は、すり足と歩行の間を行き来した。
  - 探索の幅（sigma）が約0.05まで縮んでおり、CPUの規模ではそこから伸びなかった。

## 5. GPU 学習: 二機体 × 学習シード5回（2026-11-17）

- 設定: `configs/train_full.json`（基準）と `configs/train_full_leg120.json`（脚20%増し）。機体以外は同じ

## 7. 小型機（mini）の再調整: 指令速度と報酬の重み（2026-11-17）

§6 の小型機は、転ばずに指令の速さで進むが、足を上げずに滑っていた。原因の候補（指令速度、報酬の重み）を
分けて確かめるため、機体の形は mini のまま、タスクの値だけを変えた3案を作り、学習し直した。

### 3つの案

どれも設計スクリプトの params を変えただけの、別の学習タスク（`scripts/build_robot.py --variant <案>`、mini の
6つの `--set` に下を足す）。機体のモデルは mini と同じ（sha256 まで一致）。報酬・成功条件・観測も、下の値を除いて
mini と同じ（`tests/test_vastai_config.py` で固定）。設計レポートの判定はすべて合格。

| 案 | 指令速度 [mm/s] | w_trot | w_swing | gait_lift [mm] |
|---|---|---|---|---|
| mini（§6） | 40〜160 | 0.5 | 0.5 | 10 |
| `mini-cmd` | **30〜120** | 0.5 | 0.5 | 10 |
| `mini-v3` | 30〜120 | **1.0** | **1.5** | 10 |
| `mini-lift` | 30〜120 | 1.0 | 1.5 | **7.5** |

- 指令速度: 腰の高さの比（mini 79.8 mm / leg120 106.3 mm = 0.75）で、5回とも合格した leg120 の 40〜160 を縮めた。
  評価の「歩数」は、前進が腰の高さの 0.15 倍（mini 12.0 mm、leg120 16.0 mm）以上の遊脚だけを数える。周期は 0.5 秒で
  固定なので、1周期の歩幅（速度 × 0.5 秒）とこのしきい値の比が、leg120 と同じになる（下限で 15/12 = 20/16 = 1.25）。
- 重み: v3（§2、`robot/mjcf/taskv3`）の値。
- 足上げ: 遊脚の報酬 `tanh((足の高さ − 足の半径) / gait_lift)` の目盛りを、同じ比 0.75 で縮めた（10 → 7.5 mm）。
- 学習の設定は `configs/train_full_<案>.json`。機体（bundle）と名前以外は `train_full_mini.json` と同じ（テストで固定）。

### 比べ方は公平か（成功条件と指令速度）

成功条件のうち、速度（`speed_ratio` 0.5〜1.5）は指令との比なので、指令の範囲を縮めても基準は同じ比のまま。
評価の指令は評価シードごとにタスクの範囲から引かれ、同じシードなら 30〜120 の側でちょうど 0.75 倍になる
（確かめた）。一方、歩数の条件は上のしきい値（12.0 mm）が変わらないので、遅い指令ほど1歩が短くなり、満たしにくい。

これを確かめるため、mini の5つの方策（40〜160 で学習）を、評価の指令の範囲だけ 30〜120 に変えて評価し直した
（`artifacts/compare/seeds_mini_eval_cmd_range.md`、評価は `artifacts/mini-cmd/evaluation-mini-policy/`）。

| 項目 | mini の方策、指令 40〜160 で評価 | 同じ方策、指令 30〜120 で評価 |
|---|---|---|
| 合格率 | 0.24 ± 0.36（0.00〜0.80） | 0.14 ± 0.17（0.00〜0.40） |
| 最少の脚の歩数 | 2.0 ± 3.0 | 1.1 ± 1.2 |
| 接地中の滑りの割合 | 0.83 ± 0.10 | 0.88 ± 0.11 |
| RMSトルク / 推定連続定格 | 0.67 ± 0.06 | 0.63 ± 0.05 |

遅い指令で評価しても、合格率は上がらず下がった（トルクの比はわずかに下がる）。新しい案の評価は、mini より
甘くはなっていない。案どうし（3案とも 30〜120）は同じ条件で比べている。

### 結果（学習シード 0〜2 の3回ずつ）

## 8. 小型機 mini-v3 のトルクを推定定格に収める: 周期とトルクの罰（2026-11-18）

|---|---|---|---|

### 比べ方は公平か（周期と歩数の条件）

周期を変えても、成功条件の値（`walks` の歩数 ≥ 4、1歩と数える前進は腰の高さ 79.8 mm の 0.15 倍 = 12.0 mm 以上、
`speed`、`rated`、`upright`）と評価シード・指令の値は同じ。歩数の条件への効き方は次のとおり。

- 1歩の前進は、おおよそ速度 × 周期。評価の指令の最小は 30.2 mm/s なので、しきい値との比は周期 0.5 s で 1.26、
  0.6 s で 1.51、0.7 s で 1.77。**周期を延ばすと、1歩と数えられやすくなる（条件はゆるむ方向）。**
- 一方、8秒のエピソードの遊脚の回数は周期に反比例して減る（各脚 約16 → 13 → 11回）。表の「最少の脚の歩数」が
  p6・p7 で少ないのはこのためで、すり足になったわけではない。評価で測った歩の周波数は 2.00・1.66・1.43 Hz で、周期どおり。
- 実測の1歩の前進（各脚の中央値）の最小は、mini-v3 18.9 mm、p6 21.8 mm、p7 19.7 mm、eff 22.5 mm、p7-eff 18.9 mm で、
  どれも 12.0 mm を十分に超える。最少の脚の歩数の最小も 6〜12 で、条件の 4 を下回った回は無い。
- **歩数の条件で落ちた評価は、どの案にも1回も無い。** 不合格はすべて `rated`。`rated` の条件（RMSトルク / 推定連続定格 ≤ 1.0）は
  周期に依らない。したがって、合格率の差はトルクの差と読んでよい。ただし、周期を延ばした案では「歩数」の条件がゆるんで

## 10. 分かったこと

- 学習済み方策は、固定歩容より速く、指令に正確に追従し、まっすぐ歩く。
- 一方、MG90S を推定連続定格（失速の40%）の内側で使うことと、足を上げてはっきり歩くことの両立が難しい。
  - 報酬の重みで、どちらかに振れる。
  - 連続定格はデータシートに無く、推定値。実機でサーボの温度とトルクを測り、この推定を確かめる必要がある。
- 脚を長くすると重心が上がり、必要トルクが増える。固定歩容では速度も直進性も悪化した。
- GPU で約1.6億ステップまで学習の規模を上げると、基準機体も平均 0.92 で合格した（§5）。脚を長くする効果は、
  主に滑りの少なさで、合格率の差は乱数の幅の中にある。
- 小型機（mini、228 g）は、同じタスクと報酬では、転ばず前に進むが足を上げずに滑って進み、合格率は平均 0.24 だった（§6）。
- 小型機は、報酬の重みを v3（接地位相 1.0、足上げ 1.5）にすると、5回とも足を上げて歩いた（歩数 14.4、滑り 0.24）。
  ただし、RMSトルクが推定連続定格を平均6%超え、合格率は 0.48 だった。指令速度を脚に合わせて縮めるだけでは、かえって滑った（§7）。
- mini-v3 の歩き方のまま、推定定格を超えるトルクの罰を 0.3 から 1.0 に強めると、トルクの比が 0.80 に下がり、合格率は5回で 0.88 に
  上がった（滑り・傾き・移動コストも減った）。周期を 0.7 秒に延ばすことと合わせると、3回で 0.97（トルクの比 0.76）だった。
  周期を延ばすだけでは、はっきりとは効かなかった（§8）。
- 脚を組めるように直した mini-r2（足先の幅が左右 7 mm ずつ広い）では、mini-eff の報酬は合格率 0.50、トルクの比 1.07 に悪化し、
  mini-p7-eff の報酬は合格率 0.90、トルクの比 0.75 と mini の結果をほぼ保った。最終の案は mini-r2-p7-eff（§9）。
- 実機との差（足の摩擦、サーボの遅れ・剛性・トルク、制御周期のゆらぎ、ガタ、質量・重心、押し）に、今の候補 mini-r2-p7-eff は
  滑りやすい足（μ 0.3〜0.5）と PWM の周期ぶんの遅れのゆらぎに弱かった。実機を想定した幅で全部を一度に変えると、合格率は 0.60。
  これらを学習に入れた mini-r2-p7-eff-dr は、普通の評価で5回とも合格 10/10、実機を想定した幅で 0.84、滑りは 0.38 → 0.27。
  押しへの強さはほとんど変わらなかった。実機の候補を dr の乱数 4 の回に替えた（§11）。
- しっぽ（1関節・2関節）を付けた四足は、同じ dr の学習で合格率 0.80・0.82 と基準（1.00）より下がり、重さのぶんトルク比が 0.61 → 0.74〜0.77 に
  増えた。押し 2.0 N では倒れにくくなった（重さの影響を含む）。3本足は、どの1本を上げても静的に立てない足の配置と、床の高さの点で速度を読む
  報酬の抜け道のため、すり足のまま一度も合格しなかった（§12）。

## 11. 実機との差に強くする: ドメインランダム化と押しの評価（段階A-2、2026-11-18）

実機は PLA の脚＋ゴム足、MG90S ×8、ESP32-S3、20 ms 周期。§9 の最終の案 `mini-r2-p7-eff`（合格率 0.90 ± 0.22、トルク比 0.75、
滑り 0.38）が実機との差にどれだけ弱いかを数字で出し、その差を学習に入れた案と比べた。

### 評価のしかた（`q8/robustness.py`、`evaluation/evaluate_robustness.py`）

評価そのものは **エンジンの評価**（`CadexDynamics.evaluate_success`。`cadex evaluate` と同じ関数）をそのまま使う。成功条件・
評価シード（2101〜2110）・指標・タスクのランダム化は普通の評価と同じで、そこに実機との差を重ねる。

- モデルの値: エンジンがモデルを読む `load_model` を包み、読んだ直後に、足と床の摩擦（床も同じ値にする。接触は大きい方を
  とるため）、サーボの剛性（比例ゲインとバイアスに同じ係数）とトルクの上限、胴体の質量と重心を書き換える。
- 時間の差: エンジンの1制御（20 ms）は `mj_step` を10回（2 ms ずつ）呼ぶ。その `mj_step` を包み、2 ms ごとに次を入れる。
  - サーボの遅れ: 方策の指令が、遅れて届く（純粋な遅れ）。
  - 制御周期のゆらぎ: 指令ごとに 0〜jitter の遅れが足される。20 ms は、50 Hz の PWM の周期に合わせて届くのを待つ場合に相当する。
  - ガタ（全幅）: 指令と関節角の差が ±幅/2 の内側ではサーボが押し返さない不感帯。ギアの衝突は表さない近似。
  - 押し: 3.0 秒目に、胴体の重心へ、向きに対して真横（左右）の水平な力を 0.1 秒。
- 何も変えない条件では、エンジンの評価と同じ数字になる（`tests/test_robustness.py`、保存済みの `cadex evaluate` の結果と
  1e-15 の丸めの差まで一致）。

組は4つ。各回 290 エピソード、手元の CPU（14 並列）で約 10 秒。

| 組 | 中身 | エピソード |
|---|---|---|
| nominal | 何も変えない | 10 |
| sweep | 1つずつ変える: 摩擦 0.3・0.5・0.7、遅れ 20・40 ms、ゆらぎ 4・20 ms、ガタ 2・4°、剛性 ×0.6、トルク ×0.8、胴体の質量 ×1.2、重心 x ±5 mm・y +3 mm | 各 10 |
| random | 実機を想定した幅から全部を一様に引く: 摩擦 0.3〜1.2、剛性 ×0.7〜1.3、トルク ×0.8〜1.1、胴体の質量 ×0.9〜1.1、重心 x ±5 mm・y ±3 mm、遅れ 0〜30 ms、ゆらぎ 0〜4 ms、ガタ 0〜3° | 50（評価シードごとに5組） |
| push | 横から 1.0・1.5・2.0・2.5 N を 0.1 秒（機体の重さは約 2.16 N。2 N で横向きの速度が約 0.9 m/s 変わる）× 左右 | 各 20 |

「倒れずに戻った」は、最後まで転倒・沈み込みが無く、押しの終わりから 1.5 秒以内に傾き 10° 以下が 0.5 秒続き、
押しの終わりの 1〜3 秒後に指令の 0.5 倍以上の速さで前へ進んでいること。合格率は普通の成功条件（`completes`・`upright`・
`walks`・`speed`・`rated`）で判定する。押しの強さは、今の候補 s3 が 1.5 N まで全部戻り、2.0 N で半分が倒れたことから決めた。

### 今の候補（s3）の弱さ

### 3本足が歩けない原因

別の調査（評価トレースから姿勢を作り直し、MuJoCo で静的な釣り合いと1本上げの試験をした）で、原因は二つと分かった。

1. **物理（主な原因）。** 今の足の配置（前の2本と後ろの中央の1本。どの脚も前後のピッチの関節だけ）では、どの1本を上げても重心が
   残る2本の支持線の外に出て、静的には立てない。立位のまま上げると、重心は支持線の外に lf で 19.8 mm、rf で 31.9 mm、hc で 43.2 mm 出る。
   関節と胴体の傾きを選び直しても、rf は胴体を 15° 傾けてもまだ 7.9 mm 外に出る（乱数で探した最良の値）。上げた瞬間に倒れ始め、その時定数は
   約 0.08 s（重心の高さ 65.6 mm）。hc の足先が y = +11 mm にずれていることが、rf を特に不利にしている。
2. **報酬の抜け道。** 追従の報酬が読む前進速度 `vel_x` は、胴体 `c_chassis` のボディ原点の速度で、その原点は床の高さにある。胴体を前後に
   揺するだけでこの点が前後に動くので、実際にはほぼ進まずに（約 10 mm/s）、追従の報酬の約 60% が得られていた。`gait_mode=0`（free）の
   足上げの報酬も、静的に上げられる hc の足踏みだけで受け取れていた。

学習は 200〜300 反復で頭打ちになっていた。物理の制約なので、学習シードや反復を足しても抜け出せる見込みは低いと判断し、**3本足の追加の学習はしていない**。
実機との差と押しの評価も、普通の評価で合格が 0 なので行っていない。

### 次の課題（3本足を直す案。どれも未検証）

1. **追従の速度を、全体の重心の速度にする。** `vel` の観測を `component_linear_velocity`（`c_chassis`）から Cadex の
   `centre_of_mass_velocity` にする。揺するだけで得られる報酬が消える。同じ穴は四足のタスクにもあるので、四足も学び直して確かめる。
   これだけで3本足が合格する見込みは低い。
2. **wave を「倒れ込みながらの短い一歩」に合わせる。** 周期を 0.45〜0.5 s にし、足が上がっているべき時間を 0.12〜0.15 s に縮める
   （今は 0.25 s で、倒れる時定数 0.08 s に比べて長すぎる）。押しとランダム化を初めは弱め、探索を長く保つ。free は使わない。
3. **hc の足先を重心の真後ろ（y ≈ −1 mm）に置く。** rf を上げたときの不足が 13.3 mm から 5.4 mm に減り、lf と rf がそろう。

## 14. 横の関節を足した3本足: tri3-r8 と tri3-r9（シミュレーション、2026-11-19）

§13 の tri-r2-dyn は、静的な不足を 4.4 mm まで減らしても、動的な一歩を学ばなかった。そこで、付け根にロール（前後の軸まわりに脚を横へ開く関節）を足した

### 設計の判断（なぜ横の関節か）

- **今の3本足が歩けない理由**: 1本を上げると、残りは2本の足になり、支えは2点を結ぶ線だけになる。四足のトロットも支えは対角の2本の線だけだが、
  その線が重心の近くを通るので歩ける。今の3本足は前後に振る関節だけで足を横へ動かせないため、右前を上げると、残りの線が重心から 4〜13 mm 離れる
  （tri-r2-dyn は -4.4 mm）。
- **直し方**: 付け根にロールを足す。足を左右へ運べるので、上げる脚ごとに、残る2本の線を重心の真下へ持ってこられる。3本足の一歩一歩を、トロットと同じ条件にする。
- **2種類を同時に試す**:

  | 機体 | ロールを付ける脚 | 関節（サーボ）の数 | 基板 |
  |---|---|---|---|
  | tri3-r8 | 前の2本だけ（`leg_roll=1`） | 8 | 今の ESP32-S3 の8チャンネルに収まる（関節の名前の対応は直す） |
  | tri3-r9 | 3本とも（`leg_roll=2`） | 9 | LEDC は8チャンネルなので、PWM 基板（PCA9685）か MCPWM が要る |

- **ほかは tri-r2-dyn と同じ**: 後ろ足は真ん中（`hc_foot_center=1`）、速度は重心で測る（`vel_source=1`）、波の歩き方（`gait_mode=1`）、周期 0.7 s。
  遊脚のしきい値は既定の 0.5 に戻す（tri-r2-dyn の 0.8 は、すり足に落ちたため）。
- **足の裏（パッド）は足さない**（YAGNI）。足首が無いと、平らな裏は脚の傾きで角だけが当たり、支えは広がらない。ロールで足りなかったときの次の手とする。
- **実機の書き出し（ESP32）は扱わない。** `deploy/esp32` は8関節で決め打ちで、tri3 の方策は書き出しで断られる。合格した機体が決まってから、別の計画で

- **前の2本の足（lf と rf）は、はっきり一歩ずつ出るようになった。** 8秒の歩きで11歩ほど。§13 の tri-r2-dyn では rf が0歩だった。
  横の関節で支えの線が重心の近くに来たことが、少なくとも静的には効いたと読める（動的に効いたかどうかは、ほかの原因と分けていない）。
- **後ろの足（hc）は、全回で0歩で、床を引きずっていた。** tri3-r8-dr の s1 の1シードだけ3歩出たが、ほかは0歩。
  「歩数の最少の脚」で見る合格条件（4歩以上）は、hc が上がらない限り満たせない。
- **滑りの罰は、hc を上げなかった。** 速さを下げ（r9 で 0.97 → 0.64、r8 で 0.77 → 0.64）、傾きを増やし（r9 で 9.7° → 12.1°）、
  モーターの負荷も上げた（r9 で 0.73 → 0.94）。r8 の傾きはほぼ変わらない（10.0° → 10.1°）。滑りの割合も下がらず、少し上がった。
- **足以外の部品が床に沈んで点を稼ぐ抜け道は、見つからなかった。**

### 確かめていないこと（§14）

- 実機では何も確かめていない。tri3-r8・tri3-r9 は印刷も組立もしていない。
- hc が上がらない原因（後ろの足だけ、横へ運ぶ関節の使い方、報酬の与え方）は、分けていない。次の案は、hc を上げる報酬
  （脚ごとの最低歩数、または遊脚の位相で接地していることへの罰。§15）。
- 学習は、s0 は 999 反復で終わったが、遅れて始まった台の回は途中経過の時点で反復数が少なかった。最終の反復数を各回で確かめていないので、そろえた比較とは言えない。
- 実機の書き出し（ESP32）は扱っていない。tri3-r8 は関節が8個でも名前が違うので、書き出しは名前の検査で止まる。
- 実機との差と押しの評価は、普通の評価で合格が 0 なので行っていない。

## 15. 遊脚の位相で接地していることへの罰: tri3-r9-sw1 と tri3-r9-sw2（シミュレーション、2026-11-19）

§14 で、前の2本は歩数が出たが、hc は全回で0歩のまま床を引きずった。滑りの罰（接地した足の速さへの罰）は、hc を上げなかった。そこで、次は
「足を上げるべき位相なのに、接地していること」そのものへの罰を足す。**この節は枠だけで、重みの値と結果は学習後に記入する。**
シミュレーションだけの比較で、印刷と実機は範囲外。

### ねらい

- 波の歩き方では、各脚に「立つ位相か、振る位相か」の目安 `st_k`（1 が立脚、0 が遊脚）がある。遊脚の位相のとき、足が床に着いていたら罰する。
  hc のように、足を上げずに引きずる脚の、床に着いている時間を減らすのがねらい。
- 比べる相手は tri3-r9-dr と tri3-r9-slip-dr（§14）。判定は、まず「最少の脚の歩数」（hc の歩数）が 0 から出るか、次に合格率。
